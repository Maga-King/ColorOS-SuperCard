# 构建依赖审计

审计日期：2026-10-09。范围：Gradle 宿主、原资源与 DEX 合包、可选补丁再生成、Root 显示后端。本文记录本地文件和实际工具结果，不把编译成功当作手机功能验收。

## 1. 当前构建链

```text
app/src + 5 个内置资产 + Gradle 依赖
  → :app:assembleDebug → app-debug.apk

app-debug.apk + 内置 supercard-resources.apk + vendor/supercard/AndroidManifest.xml
  → tools/unified-prototype/build.py
  → 原资源 0x7f + 宿主资源 0x7e + 去重后的宿主/原卡包 DEX
  → zipalign → 签名、验签 → 统一 APK

同版本统一 APK + root-backend/module.prop + root-backend/service.sh
  → Root 后端部署材料（APK 复制为 backend.apk）
```

记忆、券码插件保持独立的资源与加载器，不将其 DEX 扁平并入主 DEX。构建不需要连接手机，也不需要设备上的钱包、小布、微信或支付宝 APK。

### 跨平台处理

合包脚本原来硬编码 Windows JDK/SDK/WinGet 路径、`.exe` 和 Java 类路径分号。迁移后应使用：

## 5. 补丁资产再生成

### 原生效补丁源

只有一个补丁器：`tools/PatchPlugin.java`。

- 卡包：原 `supercard-resources.apk` → `supercard-code.zip`，加 `--pay-density`。
- 记忆：原 `memory-plugin.apk` → `memory-code.zip`，使用三参数形式，不加 Pay 参数。
- 券码：现版本直接保留原完整 `coupon-plugin.apk`；没有遗漏的券码 DEX 补丁脚本。

通用补丁包括 OEM `setNightMode`、`bindServiceAsUser`、虚拟显示创建/释放边界。Pay 补丁仅五类中的 66 次 `dip2px` → `dip2pxDefault` 调用，工具会校验白名单外密度调用计数未变。

已使用的旧补丁环境为 WSL `/usr/share/apktool/*`：

| 包 | 本地版本 |
| --- | --- |
| `apktool` | `2.7.0+dfsg-7.1ubuntu1` |
| `libsmali-java` | `2.5.2.git2771eae-4` |
| `libguava-java` | `32.0.1-1build1` |
| `libjsr305-java` | `0.1~+svn49-12` |

`tools/RebuildPayDensity.ps1` 保留这条历史路径，其 `-Build` 分支仍含开发者 JDK/Gradle 绝对路径。标准 CI 不应调用该分支。现在已将实际旧环境所需 4 个 JAR 只读复制到 `tools/asset-patcher-libs`，合计 4172832 字节。`manifest.json` 记录包版本、每个 JAR 的 SHA-256 和许可证链接，并保留原 copyright 与 Apache 全文；见该目录 [说明](../tools/asset-patcher-libs/README.md)。

### 可选跨平台验证脚本

```sh
# JAVA_HOME 或 PATH 已提供 JDK；默认不需要 JADX、WSL 或 apktool。
python tools/rebuild_assets.py
```

脚本只在保留供检查的临时目录创建产物：

1. 默认 `bundled` 后端先验证固定 JAR 的 SHA-256，再编译原 `PatchPlugin.java` 的临时副本。源码、imports 和 opcode 策略都不改。
2. 使用原 org.jf 库，输入分别为仓库内 `supercard-resources.apk` 和 `memory-plugin.apk`。
3. 生成卡包和记忆补丁包，保留原补丁自检。
4. 比较每个解压后 DEX 的 SHA-256；ZIP 时间戳不参与此比较。
5. 默认永不覆盖已提交资产。全部 DEX 相同后，才允许显式 `--write`；任何差异返回 `mismatch` 并拒绝写入。

### 2026-10-09 默认原库后端：再生一致

Windows/JDK21 使用本次固定的原库后端，两个补丁生成成功，Pay 66 次校验通过。卡包 `classes.dex` 至 `classes4.dex` 的 4/4 DEX，以及记忆 `classes.dex` 的 1/1 DEX，解压后 SHA-256 **全部与已提交资产相同**，脚本返回成功。临时报告目录为 `supercard-assets-uaj0dxd0/asset-verification.json`。

因此默认后端可以作为 Actions 的额外资产再生校验，运行时不加 `--write`。原资产保持第 3 节的值。ZIP 容器时间不同仍可能使整个 zip 文件 SHA 不同；完整 DEX 已逐字节确认。

### 实验新版 JADX 后端：明确不一致

保留 `--backend jadx` 作为不同库的比较实验。该后端要求 `JADX_JAR`，只在临时副本迁移 imports，验证输入 DEX 为 `039` 后使用 `forDexVersion(39)`；原 Java 不改。JADX 1.5.5 对 `forApi(36)` 直接写入会报无效 DEX 版本，故该转换属于实验后端的工具兼容处理。

临时源码编译和两个补丁生成成功，Pay 66 次校验通过；卡包记录 18 种接口引用，记忆记录 6 种。但 **5 个输出 DEX 与已提交资产均不相同**，脚本因此拒绝覆盖。不能把该次再生成作为 CI 默认输入。

| 资产 | 不同的 DEX | 结论 |
| --- | --- | --- |
| `supercard-code.zip` | `classes.dex`、`classes2.dex`、`classes3.dex`、`classes4.dex` | 4/4 SHA 不同 |
| `memory-code.zip` | `classes.dex` | 1/1 SHA 不同 |

示例证据：原记忆 DEX SHA 为 `7fb6bd3088cd10e1877dff5bb10467da0e178a2b72b6e99f4782e79298b35b0a`；新实现输出为 `9b8073f71b2198257c8ab50e58d735980478fba42e02d919c9890a545458b3c4`。这是解压后 DEX 字节差异，不是 ZIP 时间戳差异。差异原因尚未逐指令审计，本文不声称语义等价。

完整本地结果位于本次脚本打印的临时目录 `supercard-assets-gdb3xuyy/asset-verification.json`；其他机器运行会生成自己的目录和报告。执行后再次核对两份原资产 SHA，均保持第 3 节的值。

## 6. Root 后端材料

`RootDisplayDaemon.java` 位于宿主源码内，由同一个 `:app` 任务编译。它依赖成品中的 HiddenApiBypass，没有另一个隐藏的 Root 后端工程、外部 dex 或原厂 .so。

`root-backend/` 当前仅有 `module.prop` 和 `service.sh`，没有自动生成 `backend.apk` 的独立 Gradle 任务。已有部署方式是把同版本 APK 复制为 `backend.apk`，由脚本执行：

```text
CLASSPATH=$MODDIR/backend.apk /system/bin/app_process /system/bin
    dev.local.supercardhost.RootDisplayDaemon
```

发布若提供后端部署包，应包含这两个文本文件和同版本 `backend.apk`，保留 shell 的 LF 换行。普通归档不自动等于已验证的 Magisk/KernelSU 可刷 ZIP；安装器与部署说明须说明实际支持的方式。不要把设备生成的 `daemon.pid`、`supervisor.pid`、日志或 `disable` 文件放入发布包。

## 7. CI 与本地一致性应验证什么

建议 Windows CI 和本地共用同一组命令及参数：

```text
校验固定二进制材料 SHA-256
Gradle Wrapper :app:assembleDebug
python tools/unified-prototype/build.py --host-apk ... --version-code ... --version-name ... --sign
zipalign 检查 + apksigner verify + 合包报告校验
```

合包已有以下检查：原 0x7f package chunk 逐字节不变、原全局字符串索引前缀不变、宿主 0x7e 独立、原/宿主类去重、Kotlin API 链接检查、不打入 libxposed 实现、资源冲突清单、16 KiB .so 对齐及签名证书匹配。

还应保存版本、JDK/SDK/Gradle/JADX 指纹、输入资产 SHA、最终 APK SHA、证书 SHA、资源校验与 DEX 报告，随 Actions artifact/Release 提供。

### 签名与逐字节比较

- 现 Gradle 宿主是 debug 构建，默认使用本机 `.android/debug.keystore`。合包的 `--sign` 会要求最终证书与输入宿主证书相同。
- CI 新生成的 debug key 与已安装版本不同。设备可直接覆盖升级的 Release 需要同一把现有签名密钥，通过 GitHub Secrets 注入，不能公开提交密钥。
- 如果合包用 `SUPERCARD_KEYSTORE`，宿主 APK 也必须由该证书签名；仅改变最终合包的密钥会触发证书不一致检查。
- 当前 Python `writestr` 和 Java `ZipEntry` 带有构建时间，APK 整包 SHA 不天然可复现。先按 ZIP 条目内容、DEX、资源包块、Manifest 和证书比对本地/CI；若要求最终 APK SHA 完全相同，还需固定所有 ZIP 时间戳及完整工具链，并单独验证签名后产物。

CI 编译/合包成功能证明材料齐全和静态检查通过；真实 Wallet API、支付虚拟屏、锁屏和手势仍属于手机运行时验证。

## 8. 不属于构建输入的本地材料

不需上传 `.gradle`、`app/build`、`build`、`tools/*-compile`、`tools/unified-prototype/out`、`vector-source`、手机日志、数据库/账号数据、截图、设置备份、PID、原签名密钥或 `local.properties`。它们不是当前构建的必要输入。

第三方工具 JAR 可以在 CI 按固定版本和 SHA 下载；不要为使用 dexlib2 把整个 Vector 工程、Android SDK 或用户 Maven/Gradle 缓存提交入库。
